# Architecture: F1 Timings

Status: approved by the owner (2026-10-25). Cited as A§x. Decisions are recorded in `docs/adr/`; this file is the overview. Facts marked **[U]** are unverified and are checked by the first phase that depends on them.

## 1. Product

- **What:** a personal website showing lap times, sector times, mini-sectors, speed traps and tyre stints for F1 sessions (FP1–3, sprint qualifying, sprint, qualifying, race). Phase 2 adds **live timing and replay**: you watch the video in the F1 TV app and follow the timing on this site, with an adjustable delay.
- **Who:** the owner only. The whole site is behind Cloudflare Access for one email address. Nothing is public.
- **Seasons:** 2023 to now in v1 (OpenF1). 2018–2022 in phase 3 (official F1 archive with the owner's F1 TV Pro). No source has sector times before 2018.
- **Non-goals:** video (F1 TV streams are DRM-protected and the ToS forbids re-serving them), telemetry traces, a car-position track map, championship standings, other users or accounts, public access, a native app, Dutch UI.

## 2. Principles

1. **Small and boring.** One user, one VM. Reuse Waterheight's stack and patterns, and drop the ops machinery that exists for a public site under load (ADR-0002).
2. **Isolated from Waterheight.** A separate compose project, database, tunnel, networks, firewall table, secrets and GIDs. Nothing in the F1 stack can break Waterheight (ADR-0003).
3. **Store raw, derive later.** Every fetched OpenF1 response and every live message is kept raw, so a parser fix can re-derive without fetching again.
4. **Honest gaps.** Missing values render as `—` with a reason in the tooltip. Nothing is invented or interpolated.
5. **One parser, one playback path.** The live feed and the F1 archive share the same SignalR topic format and one TS parser (ADR-0006). Live and replay are both "state at session time T" (ADR-0007).
6. **Never call F1 or OpenF1 from CI.** Tests use recorded fixtures. GitHub's runners are blocked by F1 anyway (FastF1 #988).

## 6. Data sources and data map

Checked against the live APIs on 2026-10-25 (Austin quali `11392`, Marina Bay race `11388`, Marina Bay sprint `11383`, Bahrain 2023 race `7953`).

### 6.1 OpenF1 (`https://api.openf1.org/v1`), v1 source

- Free, no auth, 2023+. Paid only within "live", which runs from 30 min before a session starts until 30 min after it ends. Free limit: 3 req/s and 30 req/min. `meetings`/`sessions` refresh daily at 00:00 UTC.
- Sessions per year: 2023: 118, 2024: 123, 2025: 123, 2026: 131 (including testing days and future sessions). Session names: `Practice 1–3`, `Sprint Qualifying`, `Sprint`, `Qualifying`, `Race`, `Day 1–3`.
- `meetings.gmt_offset` is a string `[-]HH:MM:SS` with no `+` for a positive offset ("-06:00:00", "02:00:00"; the committed fixtures); ingest stores it unchanged and the web parses it (P4c, A§13 Times).
- **Cancelled sessions stay listed** with `is_cancelled: true` (`sessions-year` fixture: 10 of the 131 sessions of 2026, those of the cancelled Bahrain `1282` and Saudi Arabia `1283` meetings, 10–19 April). Their data endpoints answer "No results found.". P1b stores the flag on `meeting` and `session` and never fetches a cancelled session, so it stays `scheduled` without `next_fetch_at` and P1c can tell "cancelled" from "no data".
- Known issues (open on `br-g/openf1`): null pit `stop_duration` (#484), sessions needing re-ingest (#483), wrong `tyre_age_at_start` for used sets (#473), slowness right after a session becomes free (#474).
- **During a live session every free request fails, past sessions included** (P1a, 2026-10-25 20:03 UTC, Austin race): HTTP 401 `{"detail":"Live F1 session in progress. Global API access (including past sessions) is restricted to authenticated users until the session ends. …"}`, with a link to buy a paid API key (the plan uses none). It lifted between 22:26:45 and 22:31:46 UTC, at the end of the live window (scheduled end 22:00 + 30 min), not at the chequered flag. The client reports it as `http 401` without retrying. P1b: nothing calls OpenF1 while a session in `session` is inside its window (`date_start − 30 min` … `date_end + 30 min`; a cancelled session or a row longer than 12 h opens none). The tick waits it out, the daemon's sync retries 15 min later, the backfill stops (exit 1) and a `refetch` fails with exit 1 and writes nothing (A§8). The very first sync has no schedule to check yet: a 401 there fails with `http_401` and is retried the same way.
- **A query without rows answers 404 `{"detail":"No results found."}`**, not `[]` (P1a). The client turns exactly that answer into an empty list; any other 404 is an error. Bahrain 2023 race `7953` has no `pit` rows at all.
- **Nulls** (P1a scan, 2026-10-25: the full responses of 11388, 11392, 11383 and 7953, plus `meetings`/`sessions` 2023–2026; the zod schemas in `apps/server/src/openf1/schemas.ts` follow it):
  - `laps` (2,898 rows): `date_start` 2, `lap_duration` 42, S1 102, S2 11, S3 20, `i1_speed` 618, `i2_speed` 11, `st_speed` 502, each `segments_sector_n` array 6–8, and single `null` elements inside the arrays.
  - `pit` (169): `pit_duration` and `lane_duration` 22, `stop_duration` all 169.
  - `race_control` (428): `driver_number` 336, `flag` and `scope` 191, `sector` 298, `lap_number` 39, `qualifying_phase` 408.
  - `session_result` (86): `position` 14, `duration` 30, `gap_to_leader` 16 (a number, a string such as `+1 LAP`, or Q1–Q3 in qualifying). `points` is missing from qualifying results.
  - Never null in the scan: `meetings`, `sessions`, `stints`, and the `drivers` fields A§7 stores (`country_code`, not stored, is null in 66 of 86).
  - **Deleted and reinstated laps in `race_control`** (P1c, 2026-10-27: the 454 final sessions 2023–2026 of the dev backfill). These numbers and the Q-phase check below come from a one-off, read-only run of the real `markLaps` over the dev backfill database; that script is not in the repository, so they cannot be reproduced from it. The committed fixtures and `apps/server/test/timing.test.ts` pin the rules: 3,677 DELETED messages, 3,672 in a known form (A§9), and 3,555 of those name a lap of the session: 2,983 by a unique time within 1 ms, 42 by the one exact time among several laps within 1 ms (never a different lap than `LAP n` names), 19 by `LAP n` among several, 8 by `LAP n` when no lap has the time, 503 in the LAP form. 117 name no lap: 80 carry neither a time nor `LAP n` (`… (NEXT LAP PIT)`), 29 name a car without laps in the session (support-series messages in 9223), 5 a `LAP n` OpenF1 does not have, 3 a time no lap has. 5 are in no known form (`CAR 243 TIME 0:00.000 DELETED - DOUBLE YELLOW`, `CAR LEC TIME 1:36.518 DELETED - … (Q1)`). All 26 REINSTATED messages parse and each restores the lap a DELETED message had deleted.
  - **The scan was too small** (P1b [box] backfill, 2026-10-26): about 5% of real sessions failed the P1a schemas with `schema`. Seen: a string `session_result.position` (11384), a null `stints.compound` (11246, 11342), a null `session_result.number_of_laps` (11275). Since then every field outside a row key, `meeting.year` and the session dates may be null or missing (it parses to null), a position string is kept only when it is a number ("DQ" → null; `dnf`/`dns`/`dsq` say why), and each field is bounded by its column (integers that fit smallint/int, seconds that fit int ms, text without NUL), so a value the schema accepts never fails an INSERT. (2026-11-09: the timestamp check also requires year ≥ 0001 and an offset within ±15:59, the `timestamptz` bounds that zod's format check alone let through.)
  - **Where lap values are missing** (P1d probe, 2026-10-28: the 128,497 laps of every session since 2025-01-01 in the dev backfill, a one-off read-only query, grouped by race (`session.type = 'Race'`, sprints included), lap 1, out-lap and in-lap). The rates are nulls per lap of that kind; the lap table's reasons (A§13, `missingReason` in `apps/web/src/views/LapTable.tsx`) keep only these four cases:
    - **Out-lap, S1:** null on 7,965 of 11,839 out-laps after lap 1 outside races (67 %), 65 of 1,531 in races (4 %), against 145 of 49,261 (0.3 %) and 285 of 47,424 (0.6 %) on laps that are neither out nor in. **Lap 1 out of the garage** (outside races, 3,111 laps, `is_pit_out` set) also lacks its lap time on 2,691 (86 %) and S1 on 2,704; a pit-lane start in a race lacks both on 19 of 19. Outside races, out-laps after lap 1 do not lack S2, S3 or the lap time more than other laps (lap time 75 of 11,839).
    - **In-lap:** outside races, 11,574 in-laps lack S3 on 1,663 (14 %, against 2.3 %), S2 on 571 (4.9 %, against 0.5 %), the lap time on 560 (4.8 %, against 2.1 %) and S1 on 256 (2.2 %, against 0.3 %). In races, S3 on 20 of 1,500 (1.3 %, against 0.4 %).
    - **Race lap 1 from the grid** (not an out-lap): 1,075 laps lack the lap time on 31, S1 on 41, S2 on 32, S3 on 29 (3–4 %), about ten times the other race laps (0.3–0.6 %).
    - Everything else gets "No time in the OpenF1 data".
  - **Track status forms** (P4b [box], 2026-11-07: `scripts/race-control-forms.sql`, run by the owner on the VM over the 113 races and sprints of 2023–2026, 11,274 `race_control` rows, read-only as `f1_api`; the output is counts and the digit-masked forms of the period-class messages, stewards' notes left out). The forms of the safety car, VSC, red flag, restart and chequered flag, with their rows:
    - **Safety car:** `SafetyCar` `SAFETY CAR DEPLOYED` 73 rows in 52 races and `SAFETY CAR IN THIS LAP` 62 in 47, 2023–2026. **VSC:** `VIRTUAL SAFETY CAR DEPLOYED` 34 and `… ENDING` 27 in 2023–2025, `VSC DEPLOYED` 25 and `VSC ENDING` 24 in 2026 (the 2026 wording is shorter).
    - **Red flag:** `Flag` `RED` with the message `RED FLAG` 13 times in 2023–2025. 2026 sends a red flag as category `Other`, `RED FLAG - RACE SUSPENDED`, 4 times, with no `Flag` `RED` row. The restart is `Other` `RACE WILL RESUME AT #:#` 25 times (15 plain, 6 `- STANDING START PROCEDURE`, 4 `- ROLLING START PROCEDURE`, 2023–2026). The chequered flag is `Flag` `CHEQUERED`, 112 rows in 112 races.
    - **How a period ends** (the next period form in the same race): `SAFETY CAR DEPLOYED` is followed by `IN THIS LAP` 62 times, by a red flag 9 and by the chequered flag 2; a VSC start by its ending 51, by a safety car 5, by the chequered flag 2 and by a red flag 1; a red flag by a restart 15, by a safety car 1 and by nothing 1; one red flag follows the chequered flag. So a period often has no end row of its own.
    - **Rows without a lap number:** 10 of the 11,274 (0, 1, 1 and 8 in 2023 to 2026), none of them in a period form.
    - **`lap_number` is the leader's lap** (the highest `lap_number` any driver had started by the row's `date`, over the 256 rows of the period forms): equal on 249. Every safety-car row matches; 102 of 108 VSC rows match and 6 are 1–12 laps ahead of the laps, which looks like lap data trailing race control in one race; 12 of 13 red-flag rows match and one is a lap behind; 6 rows come before any lap started.
    - **Rules built from them** (`trackPeriods`, `apps/web/src/lib/track.ts`, with the exact regexes of the query): a state machine over the rows in order, one open period per kind. A safety-car start closes an open VSC, a red flag closes an open safety car and VSC, `IN THIS LAP` and the VSC ending close their kind, `RACE WILL RESUME` closes the red flag at the lap before its own (the restart lap is green), and so does a safety-car start (`RED → SC+` once in query 3, with no restart row between), the chequered flag closes everything open, and a period still open at the end closes at the last lap number seen. A repeated start keeps the first. A row in a period form without a lap number is listed under the table and never banded. A band marks the leader's lap, so a lapped car's band can be a lap off.
  - **`date_start`** (owner, 2026-11-07, P4f; a one-off read-only query on the dev database, 2026-11-08, over the 2026 races and sprints with laps: 24 sessions, 23,280 laps; the gap chart (A§13) depends on it):
    - **Where it is null:** only on lap 1 (6 of 525), never after it.
    - **Against the previous lap:** on 22,729 consecutive pairs, `date_start(n+1) − date_start(n) − lap_ms(n)` has |d| median 51 ms, p95 164 ms, max 59,835 ms. On the 798 pairs where lap n is a pit-in lap or lap n+1 a pit-out lap: median 61.5 ms, p95 202 ms.
    - **The gap at the flag** from line crossings (the gap chart's method) against `session_result.gap_to_leader`, over 273 classified drivers: |error| median 73 ms, p95 4,982 ms, max 20,051 ms. The tail sits at about 5, 10 and 20 s, which matches post-race time penalties: the official gap includes them and the on-track crossings do not.
    - **A hole:** 11234 lacks laps of the winner, so 5 of its drivers are not comparable.
- **Weather** (owner, 2026-11-07, P5a): `/weather?session_key=` is the seventh per-session endpoint (A§8), the track-side station that the feed's `WeatherData` also carries (A§11.1): air and track temperature (°C), humidity (%), pressure (mbar, the same as hPa), rainfall, wind direction (degrees) and wind speed (m/s), one row per sample, keyed by `date`. The **[U]** facts, from the fixtures recorded 2026-11-09 (`weather-normal` race 11388, `weather-wet` the 2024 São Paulo race 9636, `weather-quali` 11392, `weather-sprint` 11383; pinned by "[U] the weather fixtures" in `apps/server/test/openf1-schemas.test.ts`):
  - **Sample interval:** one a minute, 59.77–60.23 s between consecutive rows (median 60.0 s), in every one of the four sessions; no gap.
  - **Rows outside [date_start, date_end]:** yes, the rows cover the station's feed rather than the session. They start 52 min before `date_start` in both races (11388: 11:07:56 for 12:00; 9636: 14:38 for 15:30), 43 min before in the sprint and 12.5 min before in qualifying, and end 13 min before `date_end` (11388; `date_end` is the scheduled end), 3.5 min after (11392), 28 min after (9636) or 54 min after (11383, whose `date_end` is 09:30 for a 09:00 sprint). The owner's rule (2026-11-09): the tiles, the rain periods and the session head summarise every row OpenF1 lists for the session, the hour before a race included (A§13).
  - **Rainfall:** only 0 and 1 (9636: 117 × 1 and 84 × 0; 11383: 20 × 1 of 127; 11388 and 11392 all 0). The UI reads any value > 0 as rain.
  - **JSON types:** `humidity` is a JSON number, which OpenF1 writes with a decimal point: whole in all 201 rows of 9636 (`86.0`; the fixtures re-serialise it as `86`) and fractional in 141 of 160 rows of 11388 (`69.6`), so the column is `real`. `wind_direction` is an integer in every row (0–354). Whether it names where the wind comes from or where it blows to is not documented (**[U]**), so the UI shows only its compass point. Pressure is about 927 mbar at Interlagos and 1009 at Marina Bay.
  - **A dropout comes as 0, not null** (found on the screenshots, 2026-11-09): `weather-normal` has a track temperature of 0 at 11:32:56, between 43.1 and 43.4 °C; no other air or track temperature, humidity or pressure of 0 in the four sessions (pinned in the same test). The owner's rule (2026-11-09): the stored rows keep what OpenF1 sent, and the web reads a 0 air or track temperature, humidity or pressure as no reading (`reading` in `lib/weather.ts`, A§13).
  - **Calm samples:** `wind_speed` 0 in 2 rows of 11388 (both with direction 0) and 11 of 9636 (9 with another direction, 191 to 330); direction 0 in 19 rows of 9636, 17 of them with 0.4–1.0 m/s. A calm sample counts no direction in the prevailing point (owner, 2026-11-09); a direction of 0 with wind stays N.
  - **Nulls:** none in the four sessions; every value is still nullable and bounded by its column (`real` refuses ±3.4e38 and beyond and a non-zero value that would round to 0; smallint for rainfall and the direction), the P1b lesson.

### 6.2 Official F1 archive (`livetiming.formula1.com/static`), P3 source

- Since ~15 Oct 2026 it returns 401 without a token. It needs F1 TV Access/Pro/Premium (the owner has Pro). Seasons 2018+.
- Structure: `static/<year>/Index.json` → meetings → sessions (`Path`) → `<Path><Topic>.jsonStream` (and `.json`). The topics are the same as the live feed (A§11.1), with a session-relative timestamp on each line.
- The Index `Key` equals OpenF1's `session_key` (checked on 11392, 11397 and 11404).
- A topic the session lacks answers **403**, not 404 (`LapCount` outside a race). `scripts/fetch-archive.ts` skips 403 and 404 per file and stops only on 401, since the Index has already proved the token.
- **Line format** (`.jsonStream`): a UTF-8 BOM, CRLF or LF line ends, then the time and the payload. The time is .NET TimeSpan text: 12 characters, `HH:MM:SS.mmm`, and past 24 h a day count in front, `d.HH:MM:SS.mmm`. A stream can open more than a day before its session (11404 opened 26 h 40 min before the start), and its clock runs continuously, so the first Heartbeat's `Utc` minus its time gives a t0 that holds within a few hundred ms. A `.z` payload is a quoted base64 string.
- **The final `.json` states are written later than the stream.** `ArchiveStatus` is "Generating" in the stream and "Complete" in the file, and `ExtrapolatedClock` differs. The stream carries `_deleted` keys (A§11.3) and the file holds none. Merging a stream gives the file's state apart from those two (11392, 11397).
- **The archive t0 runs late against OpenF1's timebase** by about 2 s (A§11.3, Timebase).
- **Token for local downloads:** `--token-file <path>`, a regular file with mode 0600 and one line that holds either the raw `subscriptionToken` JWT or the URL-encoded `login-session` cookie. Only the expiry is printed. The script refuses under `CI` and writes to the gitignored `fixtures-private/archive/<key>/`.
- Requests carry `Authorization: Bearer <subscriptionToken>` (A§12.3). It works from home IPs; datacenter ranges such as GitHub Actions get a CloudFront 403.

Size (measured 2026-10-26, the [box] backfill of 2023 up to the 2026 Mexican GP): 495 sessions (455 past and processed, 25 future, 15 cancelled) take **102 MB** including raw JSON: `raw_response` 21 MB (21 %, 2,730 rows), `lap` 59 MB (258,639 rows), every other table under 6 MB.

Built in P1b: `db/migrations/20261026000001_timing_tables.sql`. Every child table references `session` and `session` references `meeting` (`ON DELETE CASCADE`), except `recording` (P2c), which is `ON DELETE RESTRICT`, so a session with a recording cannot be deleted; nothing references `driver`, because OpenF1 can list a lap for a driver missing from `drivers`. The ingest fills `deleted`, `deleted_reason` and `quali_phase` since P1c (A§8, A§9); a session ingested before P1c keeps the defaults until it is fetched again.

Roles (owner, 2026-10-25; built in P1b): `deploy/postgres/roles.sql`, a PostgreSQL init script that runs once when the volume is created, makes the logins `f1_migrator` (owns every object), `f1_ingest` (writes) and `f1_api` (reads). Each login's password is a file secret `db_<login>`.

- It is plain SQL: a `DO` block reads each password on the server with `pg_read_file(prefix || login)`, where the prefix is the setting `f1.secret_prefix` or else `/run/secrets/db_`. In production the password never appears in SQL text or a statement log, and an error names only the login and the SQLSTATE. It is idempotent (create if missing, then `ALTER ROLE … NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`), makes `f1_migrator` the database owner, revokes every database privilege from `PUBLIC` (and `CONNECT` on `postgres` and `template1`) and grants `CONNECT` to `f1_ingest` and `f1_api`. No `CONNECTION LIMIT`: each process's pool is capped in code (2 connections).
- **One database per cluster** is a premise: roles and the `CONNECT` revokes are cluster-wide, and a database created later keeps `PUBLIC` `CONNECT`, so "no login reaches another database" holds only while `f1` is the only one (P1f can add a `pg_hba` guard).
- The `db` container must be able to read `/run/secrets/db_f1_*`: it needs the secrets' GID (`group_add`, P1f). After rotating a `db_*` secret, run `roles.sql` again by hand; it runs by itself only on a new volume.
- Grants live in `20261026000002_grants.sql`: `f1_ingest` gets `SELECT, INSERT, UPDATE` on `meeting` and `session` and also `DELETE` on the seven child tables it replaces (a `DELETE` on `meeting` or `session` would cascade through every timing table); `f1_api` gets `SELECT` on all but `raw_response`. Later phases grant their own tables (no default privileges): `20261030000001_recording.sql` (P2c) creates `recording` and `recorder_status` and grants `f1_ingest` `SELECT, INSERT, UPDATE` on both and `f1_api` `SELECT`. The `live` role logs in as `f1_ingest` (owner, 2026-10-30), the second consumer of `db_f1_ingest` after `ingest`; there is no fourth login and `roles.sql` is unchanged. `20261109000001_weather.sql` (P5a, owner, 2026-11-07) creates `weather` (`ON DELETE CASCADE` from `session`, like every child table), adds `weather` to `raw_response`'s endpoint CHECK, grants `f1_ingest` `SELECT, INSERT, UPDATE, DELETE` and `f1_api` `SELECT` on it (nothing new on `meeting` or `session`), and re-queues the final sessions (A§8). Its down migration deletes the weather raw rows first, so the old CHECK can come back; an image rollback runs no down migration, and the previous image works on the new schema (the CHECK is a superset).
- Development and tests: `apps/server/scripts/dev-db.ts` writes a random password per login on the server with `COPY … TO` (so in development the password does appear in that statement's text), sets `f1.secret_prefix`, runs `roles.sql` and empties the files again. `apps/server/test/db.ts` (`createTestDb()`) does this for each integration test file.

## 8. Ingestion (OpenF1)

- **Schedule sync:** daily at 00:30 UTC, plus at start: `meetings` and `sessions` for the current year and every year from 2023 that has no `meeting` row yet (all of them on the first run). Upserts `meeting`/`session`, metadata only. A new session is `scheduled` with `next_fetch_at = date_end + 35 min` (none when cancelled); a changed `date_end` moves `next_fetch_at` only while the session is still `scheduled`. A session whose meeting is missing from `meetings` is skipped and counted. The raw schedule responses are not stored.
  - The daemon skips the sync during a live window (A§6.1). A skipped or failed sync is tried again from the minute job at most every 15 min until it succeeds.
  - One response is one parse and one transaction: a single bad row (a missing date, a value the schema rejects) fails that year's sync, which keeps the previous schedule and shows up as `schema` or `db` in the log.
- **Per-session pipeline** (P1b, `apps/server/src/ingest/`; the rules are pure functions in `state.ts`):
  - Every minute the tick marks `scheduled`/`fetched` sessions with `next_fetch_at ≤ now` as `due`, then processes the due ones one at a time, newest `date_end` first. Cancelled sessions are never due. It waits while any session is live (A§6.1) and logs the wait when it starts and when it ends.
  - **Success at t** (after the 35 min wait, i.e. after the paid window): `fetch_count + 1`, `fail_count = 0`, `last_error = null`, then the first of `date_end + 3 h` and `date_end + 24 h` that is later than t → `fetched` with that `next_fetch_at`, or else `final`. A session older than 24 h is fetched once, so the backfill costs 7 requests per session (6 before P5a). A success before `date_end + 35 min` (only a `refetch` gets there) leaves the session `scheduled` for its first fetch.
  - **Failure n** (consecutive): `due` again at t + min(5 min · 2^(n−1), 6 h), that is 5, 10, 20, 40, 80, 160, 320 and 360 min; the 9th → `failed` (shown in the status panel, P1c). `last_error` holds the code: HTTP 429 → `rate_limited`, any other status → `http_<status>`, `timeout`, `network`, a body that is not JSON or does not match the zod schema → `schema`, a PostgreSQL error → `db`, anything else (a bug in the normaliser) → `unknown`.
  - **One transaction:** all seven endpoints (`drivers`, `laps`, `stints`, `pit`, `race_control`, `session_result` and, since P5a, `weather`) are fetched first, and any fetch or schema error writes nothing but the failure: a weather fetch or schema failure fails the session's fetch like any other endpoint (owner, 2026-11-07, P5a). Then one transaction locks the session row (`FOR UPDATE`), decides the transition from that locked row, replaces the seven `raw_response` rows and all the session's child rows (delete, then insert in chunks of 1,000 rows), and sets the state. Replace-per-session is idempotent and drops rows OpenF1 removed; the lock serialises a `refetch` against the daemon.
  - **Raw is stored in that same transaction, not first** (a P1b decision, against the PHASES wording "store raw → normalise"): the empty guard compares a new reply with the stored raw, so storing a transient `[]` first would replace the good raw and the next normalise would wipe good rows. The cost: a reply that fails the schema is not kept (only its `schema` code is).
  - **Empty guard:** an endpoint that answers `[]` where its stored `raw_response` had rows is a failure with code `empty`, and the stored data stays.
  - **Timing rules (P1c):** the normaliser applies them (deleted laps, `quali_phase`, A§9) to the lap rows before the insert, so the same transaction writes them with the rows and replace-per-session never wipes them. It takes the session's `type` from the `session` row.
  - The app clock is injected: no state decision uses SQL `now()`, so unit and integration tests run on a fake clock.
  - **In/out laps:** `is_pit_out` is OpenF1's `is_pit_out_lap`; `is_pit_in` is derived (A§9). Seconds become integer ms (rounded), and nulls stay null.
  - One log line per session: key, new state, rows per table (`weather` among them since P5a), skipped rows (another session's rows, or duplicate keys: the last wins; a weather row is keyed on its instant, so one instant in two spellings is one key), the timing rules' message counts (`rules`: `deleted`, `reinstated`, `unmatched`, `unparsed`), duration and `last_error`; a failure adds the endpoint and, for `schema`, zod's paths and codes (at most 10). Never a value, a URL, a password or a response body.
- **Rate budget:** at most 25 requests in any 60 s and 2 in any 1 s (sliding windows, shared by every call of the client), below the 30/3 limit. On a 429, honour `Retry-After` or wait 60 s. Each attempt refuses redirects, ends after 120 s in all (headers and body: `timeout`) and stops reading past 64 MiB (`schema`, not retried); a race's `laps` is about 1 MB. 7 requests per session (P5a; a session took 3.2–3.6 s in the local re-queue run below). Free requests fail with 401 during any live session (A§6.1), so the sync, the tick, the backfill and a refetch wait for the live window to end.
- **First backfill** (`backfill` role): syncs every year from 2023, then processes every session that is neither `final` nor cancelled and ended more than 35 min ago, newest first, each once per run, with the same transitions as the tick. Exit 0 when nothing failed, else 1. A live window stops it (exit 1); run it again later. ~470 × 6 ≈ 2,800 requests ≈ **1 h 55 min** (measured 2026-10-26: 1 h 54 min 44 s over two runs, see the [box] backfill below); since P5a ~470 × 7 ≈ 3,300 requests ≈ **2 h 15 min** at 25 a minute (an estimate). It's resumable, because state lives in the DB. Don't run it next to a running `ingest` daemon: each process has its own rate limiter.
- **[box] backfill** (WSL, home IP, a throw-away PostgreSQL 18). The superuser login is used because the grants are proven in CI (handoff §12):

  ```

Together 1 h 54 min 44 s. End state: 454 `final`, 1 `fetched` (the latest race, waiting for end + 24 h), 40 `scheduled` (25 future, 15 cancelled). Database 102 MB (A§7).
- **The P5a re-queue** (owner, 2026-11-07; `20261109000001_weather.sql`): the migration sets every `final`, not cancelled session back to `fetched` with `next_fetch_at = date_end + 35 min`, long past, so the running daemon's next tick marks them all `due` and fetches each once more with its seven endpoints, newest first: about 455 sessions × 7 requests ≈ 2 h 15 min, paused during live windows like any tick. No SQL `now()`: the tick's clock decides, and each becomes `final` again by the success rule above. Scheduled, due, fetched, failed and cancelled sessions are untouched, so a `failed` session gets weather only through a `refetch`. The empty guard still applies: an endpoint that now answers `[]` where rows were stored fails with `empty` and keeps the rows. Any failure of a re-queued session (a 429, a timeout, a weather `schema` error, `empty`) takes the normal backoff, and the 9th in a row makes it `failed` although it holds complete data: the rows stay, but the API then serves them `no-store`, `/status` lists the session, and a `refetch` recovers it (P5a code review). Until its turn, a re-queued session's Weather tab says "Weather is queued for a new fetch; check back later." (A§13). The down migration does not undo it. The [box] checks once it has drained: `/status` shows no extra `fetched`, and its `failed` list is the one from before the deploy. Locally (2026-11-09, a throw-away PostgreSQL 18 with 2024 and 2026 synced and 9636, 11388 and 11392 refetched): after a rollback and `migrate` the three were `fetched` at end + 35 min, and one tick fetched them back to `final` with 201, 160 and 77 weather rows, about 3.3 s each.
- **Manual:** `refetch <session_key>` (digits only, else exit 64; unknown key → exit 1) for OpenF1 re-ingests (as in #483). It processes the session now: a success makes the normal transition, a failure changes nothing (a `final` session stays `final`) and exits 1. During a live window it writes nothing and exits 1 (it does not wait: a manual command should not hang for hours).
- **Scheduling pattern:** in-process croner (UTC). One job runs every minute inside a busy guard: it syncs the schedule when due (at start, after `30 0 * * *` asks for it, or 15 min after a failed try), then ticks. A minute that fires while the job runs is remembered, and the job runs once more when it ends (missed ticks run once, the Waterheight pattern). SIGTERM/SIGINT stops the cron, lets the current session finish, closes the pool and exits 0.
- **Heartbeat:** the work touches it at start, as each OpenF1 attempt starts (after the rate limiter), after each call, after each session and at the end of each tick (a waiting one too). One attempt lasts at most 120 s (the client's deadline), within the 120 s limit (A§4), so slow but progressing work never goes stale. Staleness means an attempt that ran into its deadline, a 429 `Retry-After` over 2 min, or a database wait past its timeouts; then `f1-tick` restarts the container.
- **Database waits are bounded:** connect 10 s, a statement 60 s on the server and 70 s on the client, TCP keepalive on, so a half-open connection cannot hang the job and its busy guard.

## 9. Timing rules (pure TS in `apps/server/src/timing/`, unit- and property-tested)

- **Deleted laps** (`rules.ts`; the lap rule amended by the owner 2026-10-26 after the full-data check, A§6.1): parse `race_control.message` after collapsing whitespace. The car is taken from the text, because `driver_number` is null in the data. `CAR n (ABC)`, then `TIME m:ss.mmm` or `LAP`, then `DELETED - <reason>`, then optionally `LAP n hh:mm:ss` and ` (PIT)`:
  - `CAR 87 (BEA) TIME 1:40.294 DELETED - TRACK LIMITS AT TURN 2 LAP 3 20:07:17`
  - `CAR 11 (PER) LAP DELETED - DOUBLE YELLOW AT TURN 12 LAP 2 21:32:22`, `CAR 5 (BOR) LAP DELETED - TRACK LIMITS AT TURN 11 LAP 9 16:29:31 (PIT)`
  - without `LAP n`: `CAR 87 (BEA) TIME 1:15.197 DELETED - TRACK LIMITS AT TURN 8 (NEXT LAP)`, `CAR 12 (ANT) LAP DELETED - TRACK LIMITS AT TURN 20 (NEXT LAP PIT)`
  - The reason is the text after ` - `, without the `LAP n …` part.
  - **Which lap:** a TIME matches the car's laps within 1 ms: one → that lap; several → the one lap with exactly that time (owner 2026-10-27), else the expected lap if it is one of them, else none; none → `LAP n`. **`LAP n` is the driver's lap n in a `Race`-type session (race, sprint) and lap n − 1 everywhere else** (practice, qualifying, sprint qualifying): of the 2,784 TIME + `LAP n` messages whose time one lap has, 2,773 sit there; the 11 others are OpenF1 numbering gaps that the time already resolves. A message that names no lap is counted, never applied.
  - **REINSTATED** (26 in 2023–2026): `CAR 63 (RUS) TIME 1:27.168 WILL BE REINSTATED` and `CAR 43 (COL) LAP 13 WILL BE REINSTATED`. The same rule, among the car's laps deleted at that moment, clears the lap.
  - **Order:** the messages in date order (dates compared parsed: they mix `+00:00` and `.095000+00:00`; ties keep their order). A lap deleted twice keeps the first reason; a REINSTATED before its DELETED clears nothing.
  - A message containing DELETED or REINSTATED in no known form is counted as `unparsed`. The per-session log line carries the counts, never a message (A§8).
  - A deleted lap keeps its values and is excluded from all bests.
- **Qualifying phase** (`rules.ts`): the phase of the last `race_control` row with a non-null `qualifying_phase` dated at or before the lap's `date_start` (a lap starting exactly on a row takes the new phase; same dates keep their order). Null without such a row or without a `date_start`. Sessions without phase rows (practice, races) get null; a lap started after the chequered flag keeps that phase. **Q1 inference** (owner 2026-10-27): in a session of type `Qualifying` (sprint qualifying included) whose first phase row is phase 2, a lap that starts before that row is Q1, because OpenF1 sent that session's Q1 rows without a phase (five 2026 sessions). Checked in A§6.1.
- **Colours in the historical view (final semantics)** (`colours.ts`, per request in the `api`; no column stores them): purple = the fastest valid value of that sector or lap in the session; green = the driver's own fastest valid value; yellow = the rest; null = no value. Out-laps and in-laps are never purple or green. Live (P2) uses progressive semantics: purple/green at that moment, as on the F1 tower (`progressiveColours` in `apps/server/src/timing/colours.ts`, rules in A§11.3).
  - Valid = not deleted, not an out-lap (`is_pit_out` null counts as false) and not an in-lap. A non-valid value is yellow.
  - Each driver's own best is one lap: the minimum valid value; on a tie the earlier `date_start` (nulls last), then the lower lap number. Purple is the best own best by value, `date_start`, lap number, then driver number: the first to set it holds it. Exactly one purple per field per session, or none without a valid value (a fast-check property).
- **In/out laps** (owner, 2026-10-25): out = `is_pit_out_lap`; in = lap n when the same driver's lap n+1 is an out-lap. A last lap that ends in the pits (a retirement, a qualifying in-lap after the flag) has no out-lap after it and is not marked.
  - `pit.lap_number` is not used for this. The **[U]** "`pit.lap_number` = in-lap" held only in races and sprints. P1a checked every pit row against the out-laps of 7 full sessions:
    - The out-lap is `pit.lap_number + 1` in race 11388 (25 of 25 rows) and sprint 11383 (54 of 54).
    - A pit row is not always a stop. In sprint 11383, race control sent "ALL CARS THROUGH THE PIT LANE" under the safety car (laps 2–4). Each pass is a pit row (`lane_duration` ≈ 18–19 s), and the next lap is an out-lap, so the rule above still holds.
    - The out-lap is `pit.lap_number` itself in qualifying 11392 (90/90) and 11384 (103/103), sprint qualifying 11379 (74/74) and practice 11378 (76/76) and 11391 (92/92). Lap-1 rows with null durations there are garage exits.
  - The test `[U] pit.lap_number against the out-laps` in `apps/server/test/openf1-schemas.test.ts` pins both meanings on the fixtures.
- **Sector deltas (comparison):** per lap, `driverB − driverA` per sector. Shown only when both values exist and neither lap is deleted. `sectorDeltas(a, b)` lives in `packages/contracts` (owner, P1c), where the web (P1e) imports it. **Best-lap row** (owner, 2026-10-28): the table opens with each driver's own best lap, the lap the server colours purple or green (exactly the own best above), paired whatever their lap numbers by giving both lap number 0 in `sectorDeltas`; it is labelled with both numbers ("Best lap", then "L12 vs L15" on a second line) and is always shown: a driver without a best lap gets "L—" and `—` cells.

| `GET /sessions/:key/laps` | all laps with colours, deleted flags, `quali_phase` and stint compound, computed server-side (a race is ~1,240 rows, ~20 KB gzipped; two queries: the session lookup, then the laps with their compound) |
| `GET /sessions/:key/stints` · `/pits` · `/race-control` | as named |
| `GET /sessions/:key/weather` (P5a, owner, 2026-11-07) | every `weather` sample of the session by `date`, with the A§7 column names (`Weather` contract); `[]` when there are none. The cache rule and the errors below apply |

"Next" uses the recorder's window (`date_end` + 30 min, the exported `AFTER_MS`) without the recorder's completed-recording exclusion, so a finished session stays selectable for replay; each is null when absent. `no-store` |
| `GET /recordings` (P2e) | every recording with its session and meeting, newest `started_at` first (then `id`): `{id, session_key, year, meeting_name, session_name, session_type, date_start, started_at, ended_at, complete}`. `no-store` |
| `GET /playback/:recording/stream?at=<ms>\|live&delay=<s>&speed=<n>` (P2d) | SSE: one `snapshot` event, then `delta` and `laps` events, then `end` (A§11.3) |

- JSON uses the A§7 column names (snake_case, no mapping layer), times as ISO-8601 UTC strings and durations as integer ms. Every answer has a strict zod contract in `packages/contracts` (P1c); an integration test parses each route against it.
- `Cache-Control: private, max-age=86400` on a per-session route of a `final` session and `no-store` on everything else under `/api`: a session that is not final, `/seasons*`, `/status`, and every 4xx/5xx. TanStack Query caches on the client. So a final session stays cached privately in the browser for 24 h: a later rules change or a `refetch` shows only after that, or after a hard reload.
- Errors are fixed: a bad `key` (`^\d{1,9}$`) or `year` (`^\d{4}$`) → 400 `{"error":"bad request"}`, an unknown one → 404 `{"error":"not found"}`, anything else → 500 `{"error":"internal"}`, logged as a code. No answer or log echoes input, a header, the token or a database message.
- **The playback stream** (P2d, `apps/server/src/api/app.ts`; the engine is A§11.3):
  - **Parameters:** `:recording` is `^\d{1,9}$`. `at` is required: digits (epoch ms) or the literal `live`, and a number must lie within [`started_at`, `ended_at` ?? now]. `delay` is an integer 0–120 and only with `at=live` (default 0). `speed` is one of 1, 2, 4, 8, 16 (default 1) and must be 1 with `at=live`. A bad parameter is 400 `{"error":"bad request"}`, an unknown recording or a missing recording directory 404 `{"error":"not found"}`, both fixed as above. Access (the `/api/*` middleware) covers every route here.
  - **Path:** the directory is `/srv/f1/live` joined with the `recording` row's `path`, checked again against `^\d+-\d+$`. Nothing from the URL goes into a path.
  - **Cap:** at most 8 streams per process; over it, 503 `{"error":"unavailable"}`, `no-store`. Since P4e a paused seek opens a short-lived still-frame stream (closed by its snapshot, A§13), still at most one stream per tab.
  - **Headers:** `Content-Type: text/event-stream`, `Cache-Control: no-store, no-transform`.
  - **HEAD:** hono runs the GET handler for HEAD and `@hono/node-server` discards a streaming body without cancelling it, so a HEAD would leak a slot, a file handle and a generator until restart (Caddy allows HEAD). The route answers HEAD itself, after validation and the recording lookup and before the cap: 200, the headers above, an empty body, no generator.
  - **Write timeout:** one SSE write (or ping) that has not completed within 60 s ends the stream: the controller aborts, the generator's `finally` runs and the slot is freed. Not covered by an automated test: a stalled client needs socket buffers filled by a real recording of tens of MB or a timer injection into hono's stream internals, either slow or flaky. `createApp` takes `writeTimeoutMs` for a later test.
  - **Events:** `snapshot` `{t, state, laps, stints}`, `delta` `{t, topic, data}`, `laps` `{t, laps, stints}`, `end` `{t}` and the heartbeat `ping` `{t}` (`PlaybackPing`), with `t` in epoch ms on the receive axis (A§11.3). `data` is what `createFeed().apply` returned, and the client applies it the same way: an object merges into `state[topic]`, anything else replaces it. `laps` and `stints` are the rows of the `Lap` and `Stints` contracts (P2e): all of them so far in a `snapshot`, and in a `laps` event only the rows whose JSON changed since the last `snapshot` or `laps`, which the client puts over the row with the same (`driver_number`, `lap_number`) or (`driver_number`, `stint_number`). A `laps` event comes at most once per second of wall time after a TimingData or TimingAppData change, and one is flushed before `end`; its `t` is the receive time of the last line applied. The rows carry the progressive colours and the stint's compound, `seg1`–`seg3` and `quali_phase` are null (the tower reads the segments from the state). There is no `id:` field; the client reopens with a new `at` after an error. `end` and `ping` carry data because EventSource drops an event without any. The heartbeat is an event, not an SSE comment (P2e fix): EventSource never delivers a comment to the page, so only an event can feed the client's liveness check (A§13).
  - **Database:** one lookup at the start, then `ended_at` at most every 30 s while the reader sits at the end of the recording. No pool connection is held across a stream (the pool maximum is 2).
- **The Access JWT** (P1c, `apps/server/src/api/access.ts`; ADR-0004 amended) is checked on every `/api` request, every method and unknown paths included, by our own middleware on hono's `verifyWithJwks`, not the `hono/jwk` middleware (that one wants `Bearer <token>`, and Cloudflare sends the bare JWT):
  - The token is the `Cf-Access-Jwt-Assertion` header; `Authorization` and cookies are ignored. A header with whitespace, or a token whose header is not RS256 with a `kid`, is refused before any certs fetch.
  - Then the signature against the team's certs, the `kid`, `iss` = `https://<team>.cloudflareaccess.com`, `aud` (a string or an array holding the AUD tag), `exp` (required; hono skips an absent one) and `nbf` (≤ now + 60 s). `iat` is not checked: hono has no leeway for it, and `exp`/`nbf` cover freshness. The keys are passed in, so a token's `jku`/`x5u` is never followed.
  - Every refusal is the same 401 `{"error":"unauthorized"}`, with no reason in the answer or the log.
  - The certs (`https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`, 5 s timeout, no redirects, parsed non-strictly) are kept per process for 5 min; concurrent requests share one fetch. Only RSA keys with a `kid` are used, any other entry is skipped, and a list without one is a failure. When a refresh after the 5 min fails, the last keys serve for up to 1 h after they were fetched (each such request logs `access_certs` with `stale: true`), then 503 `{"error":"unavailable"}`. A cold start without keys answers 503 at once, logged as `access_certs`, and the next request fetches again (no negative cache). An unknown `kid` is a 401 without a refetch, so a key rotation can refuse logins for up to 5 min. A `ponytail:` note in the code names both fixes: a refetch on an unknown `kid` at most once a minute, and a 30 s negative cache.
  - Config: `CF_ACCESS_TEAM` (`^[a-z0-9][a-z0-9-]{0,62}$`, which keeps the certs URL on `cloudflareaccess.com`) and `CF_ACCESS_AUD` (`^[0-9a-f]{64}$`) from `/etc/f1/f1.env`, a Compose `env_file` (P1f). They are not secrets. Missing or malformed → the `api` role logs the variable's name and exits 78 before listening.
- `/healthz` (`select 1` → 200 `{"ok":true}`, else 503 `{"ok":false}`, `no-store`) is the only route without the JWT check. The local update smoke test uses it, and through the tunnel it still sits behind Access.

### 11.2 Recorder (`live` role)

- **Loop** (`apps/server/src/live/recorder.ts`): a tick every 30 s that always touches the heartbeat. It reads the next session (not cancelled, `date_end` + 30 min in the future, no complete recording yet, earliest `date_start`), re-reads the token file, logs in when A§12.3 says so, checks the disk and writes `recorder_status`. One recording at a time: an overlapping session starts late.
- **Start:** 60 min before the session's `date_start` (FastF1: "recording may need to start up to one hour before"). The directory is `/srv/f1/live/<session_key>-<startedAtMs>/` and its `recording` row is relative to `/srv/f1/live`.
- **Line format:** one JSON array per line, `[receivedAtMs, topic, payload, f1Timestamp]`, and `[receivedAtMs, "_subscribe", result]` for the full state that a `Subscribe` returns. The 3-element line of the first plan is not enough: `parseFeedLine` (`apps/server/src/live/read.ts`) takes the event time from the 4th element and a `full` event per topic from `_subscribe`, and the duplicate check in `createFeed` keys on that time. Without both, the duplicates a reconnect replays would not be recognised. Every line goes out with one `writeSync`, so there is no buffer to lose.
- **Files:** `feed.jsonl` is the current segment. After an hour it is renamed `feed-<firstReceivedMs>.jsonl` and gzipped in the background to `feed-<firstReceivedMs>.jsonl.gz`; the plain file goes only after the gzip succeeded. `snapshots/<ms>.json.gz` holds the full state every 30 s (written through a temporary name, skipped while the previous one runs; `<ms>` is wall-clock time). Files are `0600`, directories `0700`, owned by 62532.
- **Stop** (`decide`, run every tick on the session row read again from the database):
  - Cancelled, or moved so that now is before `date_start` − 60 min: stop, incomplete (it is not marked finished, so the moved session is recorded when its time comes).
  - `SessionStatus: Ends` seen after a `Started` seen in this recording: stop at `Ends` + 30 min. An `Ends` before any `Started` is ignored, because the subscribe's full state can still hold the previous session's status (A§11.1).
  - Now ≥ `date_end` + 30 min and no `Started` seen: stop. Once one was seen, the recording waits for `Ends`: past the planned end the status can be `Finished` or `Inactive` between qualifying segments, so no status short of `Ends` means the session is over. That covers a red flag too.
  - Now ≥ `date_end` + 3 h: stop whatever the status.
- **Reconnect:** backoff 1 s doubling to 30 s, back to 1 s after a connection that lasted over 60 s. Every connect subscribes again and writes a `_subscribe` line; the merge logic tolerates the duplicates (`apps/server/test/feed-recorder.test.ts` replays after a drop against a fake SignalR server). A negotiate answered 401 or 403 is `feed_unauthorized` (A§12.3).
  - **Measured** (A§11.1): F1 closed all three race connections with 1006 about 1 h after their previous connects, while the FP1 connections held for 2.45 h, so there is no proven fixed limit. The merge recovered every lap and sector time across the race drops: all three race recordings equal the archive on laps 2 and later (A§11.3).
- **`complete`** is true when the recording reached a normal stop (not a cancel or move, not a disk failure, not a SIGTERM), saw `Started` (a postponed session, or a feed with only `Heartbeat`, is not complete), was subscribed at least once, carried a token on every connection that overlaps `date_start` … `date_end`, and had no disconnect over 60 s between `date_start` and `date_end`. The time from `date_start` to the first subscribed connection counts as a gap, so a late start is not complete; flaps before `date_start` (the −60 min window) do not count. Without a token at session time the recorder still records, anonymously (17 of 19 topics), and `complete` stays false.
- **Disk:** free space under `/srv/f1/live` is read every tick; under 5 GiB the status warns `disk_low`. A failed write (a full disk), or under 1 GiB free (the floor: the disk may be shared with PostgreSQL, so the recorder stops before a write fails), ends the recording with `disk` as `last_error` and `complete = false`. No recording starts under the floor, nor for 5 min after a disk end or the last tick under the floor.
- **Restart:** at boot every `recording` row without `ended_at` is closed (`ended_at` = now, `complete = false`) and its leftover plain segment gzipped. A restart in a session therefore gives a new directory and row; one past `date_end` + 30 min is not resumed. SIGTERM closes the socket, gzips the last segment and closes the row (`stop_grace_period: 60s`).
- **Logs:** pino with fixed codes and non-secret fields only: never a token, password, cookie, URL, payload or the server's close text.

### 11.3 Parser and playback

- **One parser** (`apps/server/src/live/`) merges topic deltas into a typed state. F1 deltas are partial objects; arrays arrive as index-keyed objects (`"Lines": {"1": {...}}`). The same code reads archive `.jsonStream` files in P3 (ADR-0006). Pure code: `read.ts` (input → events), `merge.ts` (`createFeed`: events → state, with the duplicate filter), `laps.ts` (deltas → `lap`/`stint` rows). `merge()`, `Obj` and the typed views (`view`, `Views`) live in `packages/contracts/src/live.ts` since P2e, because the web client applies the stream's deltas with the same code; browser-safe, zod is the only import.
- **Input** (`read.ts`): every input becomes `FeedEvent {t, topic, payload, full?}`.
  - A P2a `feed.jsonl` line `[receivedAtMs, topic, payload, f1Timestamp]` is one event at the F1 timestamp, or at `receivedAtMs` when that is missing (the native client writes it as `"undefined"`, the library client as null). `[receivedAtMs, "_subscribe", result]` is the `Subscribe` completion's full state: one `full` event per topic at `receivedAtMs`, SessionInfo first (SignalR Core has no classic `R` message, P2a).
  - An archive file has the line format of A§6.2. A `.z` payload stays a raw string. `CarData.z` and `Position.z` are recorded, never parsed. A line with a bad time or bad JSON is skipped and counted.
  - Durations (`duration()`, FastF1 `to_timedelta`): `h:m:s.f`, `m:s.f` or `s.f`; the fraction is cut to µs, then rounded to ms.
- **Merge semantics** (`merge()` in `packages/contracts/src/live.ts`; the duplicate rule is `createFeed`'s):
  - Objects merge key by key. An array in a delta is an index-keyed object (`[a, b]` is `{"0": a, "1": b}`), so the state holds no arrays. A leaf replaces; an object replacing a leaf, or the reverse, replaces too.
  - `merge` returns the **effective delta**: only what changed, as fresh objects that never alias the state. A new object counts as changed even when empty, so merging the effective deltas from empty rebuilds the state.
  - An exact duplicate (same topic, `t` and payload) within 5 min of feed time is dropped, because a reconnect replays messages.
  - A full state is applied as its effective delta (what it changes, or nothing) and is never deduplicated.
  - `_deleted: [keys]` removes those keys from the object it sits in. The effective delta lists the keys really removed. The stream needs it (11392: `"_deleted":["Lap"]` under `BestLapTime`) and the final `.json` states hold none.
  - A null or undefined payload is ignored. A payload that is no object (a `.z` string) replaces the topic's value.
  - Input is untrusted: state objects have no prototype, reads are own-property only, the keys `__proto__`, `constructor` and `prototype` are dropped, and an object nested deeper than 32 levels is dropped.
- **Typed views** (`packages/contracts/src/live.ts`): one zod 4 `looseObject` per topic (DriverList, TimingData, TimingAppData, TimingStats, SessionInfo, SessionStatus, SessionData, TrackStatus, LapCount, RaceControlMessages, ExtrapolatedClock, WeatherData). Every field is optional, a bad leaf becomes undefined (`.catch`), so one odd value never hides a topic, and unknown fields pass through. Index-keyed collections are records.
- **Gap fields per session type** (2026-11-07, the design review's [U] in `docs/design/2026-11-redesign/README.md`, "Found in passing"): TimingData lines carry different gap fields per `SessionInfo.Type`.   - **Race:** `GapToLeader` and `IntervalToPositionAhead.Value` (and `Catching`). The leader's are `LAP <n>`, a lapped car's gap `<n>L` or `<n> L`.
  - **Practice:** `TimeDiffToFastest` and `TimeDiffToPositionAhead` on the line, empty for the fastest driver and for a driver without a lap time. The live recording carries the same two.
  - **Qualifying:** per part only, `Stats.<i>.TimeDiffToFastest` and `Stats.<i>.TimeDifftoPositionAhead` (a lower-case "to": `TimeDiffToPositionAhead` never appears in qualifying), with the part's best lap in `BestLapTimes.<i>.Value`. `<i>` is `SessionPart − 1`: 2,835 of the 2,838 indexed `Stats` deltas and all 1,065 `BestLapTimes` deltas write that entry, the other 3 the previous part's. `SessionPart` is 0 in the first state of 7 of the 9 sessions, for under 10 s, then 1 to 3. `NoEntries` lists the cars per part (three counts); the tower does not read it.
  - Sprint Shootout and Sprint Qualifying are of type `Qualifying`, sprints of type `Race`.
  - **The tower on the same data** (`towerRows` every 10 s of feed time, a one-off run outside the repository): in practice (6 sessions, 41,070 rows) Gap shows on 64.3 % of rows, 0 % before this fix; `—` says "No lap time yet" on 31.1 % and "Fastest lap" on 4.7 %. In races (223,887 rows) 80.6 %, as before: "Retired" 3.2 %, "No gap in the feed" 16.2 %, 60 % of them before any car has completed a lap. Int shows on 64.3 %, 47.9 % and 79.6 %.
  - **[box] (owner, 2026-11-07):** the same on 2026 data, from the F1 archives with `node scripts/feed-keys.ts fixtures-private/archive/11392 fixtures-private/archive/11397 fixtures-private/archive/11404` (or a recording's `feed.jsonl`; key paths and message counts per session, no values). - **Lap reconstruction** (`laps.ts`) from `TimingData`/`TimingAppData` produces the `lap` and `stint` rows OpenF1 builds, incrementally. **FastF1 is the base** (MIT, notice kept in the ported files). **Where it disagrees with OpenF1, OpenF1's behaviour wins** (owner, 2026-10-29): OpenF1 is the oracle and the v1 source. Each rule below says its origin.
  - **Licence:** OpenF1's code (`br-g/openf1`) is CC BY-NC-SA 4.0. It was read at `a33391239e4e` for behaviour only and is never copied: no code, no comments. The rules below are our wording of observed behaviour.
  - **Session gate:**
    - A feed joined before a session carries the previous session's full state until F1 switches: SessionInfo `Key` and `Type`, `NumberOfLaps`, Stints, and race control including the chequered flag. In Mexico FP1 (11397) the three `Subscribe` states held the Austin race, 11396.
    - The switch is a `_kf` keyframe: SessionInfo with the new `Key` first, then TimingAppData with empty Stints and TimingData lines without `NumberOfLaps`. It came about 12 min before the start in 11397 FP1.
    - `createLaps` counts only events from a SessionInfo with its own `Key` until one with another `Key`. `parseFeedLine` puts SessionInfo first in a `Subscribe` state, so the gate opens before the other topics are read. Without the gate the first FP1 run matched 40.16%.
    - A race is a session of `Type` "Race", sprints included (OpenF1 behaviour).
  - **Lap numbering and start:**
    - A driver seen for the first time has lap 1. A `NumberOfLaps` count above the current lap's number starts a new lap, without filling gaps. In a race the lap is count + 1, because the start crosses no line. A count that is no integer skips the rest of that driver line. (OpenF1 behaviour; FastF1's own lap counter is not used.)
    - A lap's `date_start` is the time of the first count that names it. Only `NumberOfLaps` sets it, and `Started` in a race (below).
    - Laps ignore TimingData until a TimingAppData line has non-empty Stints (OpenF1 behaviour). Stints are not gated.
  - **Times:**
    - An end-of-lap value (lap time, S2, S3 and their segments) that arrives less than 10 s after the current lap started belongs to the lap before, and is dropped when there is none. S1 and its segments go to the current lap. (OpenF1 behaviour; FastF1's 5 s window is not used.)
    - A sector is read only as an object keyed 0 to 2: the list form carries no values (FastF1 and OpenF1). Its value must be plain seconds (`33.456`); `1:05.123` is no value (OpenF1). A time over one day is no value.
    - A new sector time fills a missing lap time with the sum of the three sectors, when all three exist (OpenF1 behaviour; FastF1's checks on it are not used).
    - Speed traps I1, I2 and ST go to the current lap; FL is not stored (OpenF1).
    - Any `PitOut` but null marks the current lap as an out-lap, `false` included (OpenF1 behaviour; FastF1 ignores `PitOut`). In-laps come from `markPitIn`, shared with the ingest (A§9).
  - **Segments:** the first segment status of a sector on a lap creates the list (holes are null) and counts as a change. Later ones are written in place and do not count as a change (OpenF1).
  - **Race lap 1:**
    - A `Started` status in SessionData gives every driver whose only lap is lap 1 its `date_start`, at the status's `Utc`, overwriting (OpenF1).
    - When lap 2 starts: a missing lap time is lap 2's start minus lap 1's, then a missing S1 is the lap time minus S2 and S3. Both only when positive. They are set directly and do not mark lap 1 (OpenF1).
  - **Chequered flag:** the time of the event whose race-control text equals "CHEQUERED FLAG" (the whole text, any case), the last one winning. A race lap that started after it never shows (OpenF1).
  - **When a row shows:** a lap's row is its copy as of the last time it is emitted: after each driver line of a TimingData message, for the laps with a changed value (OpenF1). So a value written in place later (a segment) or set directly (race lap 1) shows only once the lap changes again.
  - **Stints** (OpenF1 behaviour):
    - A driver's first TimingData line creates stint 1, and `NumberOfLaps` is the last stint's `lap_end`, raw (no race +1).
    - TimingAppData: the key + 1 is the stint number, in key order as text. A list (the feed's form at the start of a session) all goes to stint 1, where FastF1 numbers it by position.
    - The compound is taken when given. `tyre_age_at_start` takes every `StartLaps` but null, the latest winning, and `TotalLaps` only while it is still null.
    - A new stint starts at the last stint's `lap_end` + 1. When it comes less than 10 s after the driver's last `NumberOfLaps`, that lap is the new stint's and the last stint ends one lap earlier.
    - A stint shows from its first changed value, with its current values.
  - **Progressive colours** (`progressiveColours`, `apps/server/src/timing/colours.ts`): the tower colours as of the moment the caller shows. Per field the values go in the order they were set (`at` on each reconstructed row; ties by driver, then lap; a value with no time goes last). A value of a deleted lap, out-lap or in-lap is yellow. Otherwise strictly below every earlier eligible value in the session: purple (the first to set a time holds it); strictly below the driver's own earlier eligible values: green; else yellow. No value: null.
  - **Timebase:** recording events use F1's own message timestamp, which equals OpenF1's `date_start` exactly (0 ms on 11397). Archive events use t0 from the first Heartbeat (A§6.2), which runs late against OpenF1 by +2021, +2018 and +2239 ms on 11392, 11397 and 11404. OpenF1 takes its archive t0 from the `.z` topics.
  - **The oracle has holes.** OpenF1 serves live-ingested rows. In race 11404 it lost about 30–45 s of messages around 20:08:2x–20:09:06 UTC, which gave 9 drivers' lap 5 merged into their lap 4, a null S2 or S1 on lap 4 for 13 drivers, and a compound stuck at UNKNOWN for one driver. The F1 archive and our three recordings agree with each other there. An OpenF1 mismatch needs the archive as referee.
- **[box] results** (`scripts/compare-laps.ts`, laps within 1 ms; the bar is 99%):
  - 11392 Austin qualifying (archive, 2026-10-30): 280 of 280, stints 90 of 90.
  - 11397 Mexico FP1 (three recordings and the archive, 2026-10-30): 589 of 589 each, stints 92 of 92 each. No difference in pit flags, speeds or segments.
  - 11404 Mexico race (2026-11-02): each recording 1338 of 1369 (97.74%) raw and 1338 of 1338 (100%) without the OpenF1-gap class. The archive 1316 of 1369 raw and 100% without the OpenF1-gap class and the lap-1 timebase class (limit B).
  - **Owner decision (2026-11-02):** the bar excludes an OpenF1-defect class that the archive referees.
- **Known limits** (owner decisions, 2026-11-02):
  - **(B) An archived race's lap 1 is about 2.2 s long.** Lap 1's start comes from the absolute `Started` Utc, while later laps use the Heartbeat t0. The 2.2 s lands in lap 1 and its S1 (22 laps on 11404) and can shift lap-1 segment statuses through the 10 s window. Taking the archive t0 from the `.z` topics, as OpenF1 does, fixes it: a P3a follow-up.
  - **(C) A lap start can carry a Subscribe state's receive time.** When the start was first seen in a Subscribe state, its date is that state's receive time (+1.7 to +4.7 s on 4 laps in one recording).
  - **(D) A Subscribe state can roll back newer values.** The state can be older than messages that arrived on the new connection just before its completion, and merging it afterwards rolls those values back (seen as one segment status). A fix needs message ordering: a follow-up, kept out of P2d (owner, 2026-11-04).
  - **(E) A `_kf` keyframe is merged as a delta**, so the previous session's lines stay in the merged state (32 TimingData lines instead of 22 right after the 11397 switch). Lap rows do not depend on it; typed views and a later full state's effective deltas do. **Fixed for the playback stream in P2e** (owner, 2026-11-05; the switch reset below). `createFeed` itself is unchanged: moving the rule there is P3a.
- **Playback (ADR-0007; P2d, amended P2e; `apps/server/src/live/playback.ts`):** the client asks for "state at session time T". The server replays the recording from its first line up to T through one `createFeed` and one `createLaps` (`recording.sessionKey`, source `f1-live`), sends one `snapshot` SSE event, then streams `delta` and `laps` events at `speed`. The route and its bounds are in A§10.
  - Live: T = now − delay. Replay: T = `at` + elapsed wall time × `speed`.
  - Moving the slider, pausing or seeking = a new SSE request.
  - Recordings stay replayable forever, in sync with the F1 TV replay.
- **Time axis** (P2d): the line's `receivedAtMs` (element 0), which is also the clock of the recorder's snapshot names. `at` is epoch ms on that axis, written `at=<ms>|live`, and so is every event's `t`. `FeedEvent.t` (F1's own timestamp) is used only to recognise duplicates.
- **The seek replays from the first line** (P2e, owner decision 2026-11-05; ADR-0007 amended). Playback no longer reads snapshot files and no longer primes the duplicate filter: one `createFeed` sees every line, so a reconnect's duplicate is dropped exactly as in the recorder's own merge. The recorder is unchanged (it still writes snapshots). Why: a P2d snapshot holds no lap history, so the nearest-snapshot seek (snapshot + 10 min of priming) gave only the current state, and a lap table could not be rebuilt from it.
  - **Cost** (local P2a recordings, WSL, `main`'s parser; counts and timings only): a full replay in process takes 1.1 s for the 4 h Mexico race (11404: 99k lines, 1369 laps) and 0.37 s for FP1 (11397). Over HTTP through the local `api`, the first complete snapshot arrives after 0.98–1.20 s at the race's end (641 KB, of which lap rows 541 KB; 1369 laps, 80 stints) and after 47–61 ms at its start. A `ponytail:` note in the code names the ceiling: a full scan and about 0.65 MB of uncompressed SSE per open for a full race (Caddy leaves the route uncompressed), bounded by the 8-stream cap. The VM has 1 CPU, so its time is unmeasured. Each committed paused seek is now a still-frame open (P4e), so the same full-scan snapshot per open; the 400 ms debounce and one stream per tab bound it. Fixes if it hurts: a per-recording scan cache, slimmer or compressed lap rows.
  - **The session switch resets the state.** Before a `SessionInfo` whose `Key` differs from the state's current one is applied, the stream clears the state, and it sends a fresh `snapshot` instead of the delta. The laps engine keeps going (it holds the recording's session only and has its own gate, above). Evidence: FP1 11397's merged state ended with 32 TimingData/DriverList/TimingAppData lines for 22 drivers and 171 race-control messages instead of 67; with the reset it has 22/22/22 lines and 67 messages. The lap and stint rows are byte-identical with and without the reset on 11397 and 11404, so the [box] results above hold. This fixes limit E for the stream only. The unit test "a session switch clears the state" covers it with a synthetic switch.
  - Measured on the 2026 Mexico race recording: its red flag arrives only in `SessionData.StatusSeries` (Aborted, TrackStatus Red; no RC `Flag: RED`), and after the switch its series still holds a `Started` from the day before; markers therefore come from the series alone and are drawn only inside the recording.
  - **StatusSeries words and incident messages** (P4e, owner's machine, 2026-11-08; counts and enum words only, nothing copied): the `TrackStatus` words of `SessionData.StatusSeries` match the TrackStatus topic's `Message` one to one. Session 11392: AllClear 1, Yellow 1. 11397: AllClear 3, Yellow 4, VSCDeployed 1, VSCEnding 1. 11404: AllClear 10, Yellow 8, SCDeployed 3, Red 1, VSCDeployed 1, VSCEnding 1. The order in 11404 is … SCDeployed, `SessionStatus` Aborted, `TrackStatus` Red, AllClear (2 min later), Yellow, AllClear, `SessionStatus` Started (the restart, 39 min after the red flag), SCDeployed, AllClear …: the TrackStatus clears 37 min before the restart while the session stays Aborted. So (P4e review) a red-flag band runs from the first of Aborted and Red to the next Started or Finished, Aborted closes an SC band, a red flag without Aborted (practice) ends at the next TrackStatus outside Red, and VSCEnding belongs to the VSC band (A§13 Markers). In RaceControl each incident opens with one `… INCIDENT INVOLVING … NOTED …` message (13 in 11404), followed by UNDER INVESTIGATION, WILL BE INVESTIGATED, NO FURTHER ACTION and PENALTY messages for the same incident, so the NOTED message counts the incident once.
  - **The `laps` event:** after each applied line the stream marks a TimingData/TimingAppData change; at most once per second of wall time, and after the last line of a `receivedAt`, it runs `createLaps`' rows through `progressiveColours` and sends the rows whose JSON differs from the last send (a `Map` of row key → JSON). A `snapshot` (the seek, the back-pressure re-snapshot and a switch) resets that map and carries every row. The pending rows are flushed before `end`. A lap's compound is that of the driver's stint covering it (the later of two); `seg1`–`seg3` and `quali_phase` are null.
- **Streaming:**
  - **Heartbeat:** the event `ping` `{t}` (T at that moment) after 15 s without a write, under Cloudflare's 100 s idle limit. It was the comment `: ping` until the P2e review; a comment never reaches the page's JavaScript.
  - **Back-pressure:** the stream is an async generator, so a write that has not drained stops it advancing. Once a resumed write finds the next line over 5 s of wall time behind, the lines up to T are applied silently and one fresh `snapshot` is sent. Nothing queues: the memory per stream is one state, the laps engine's rows and one read chunk.
  - **Tail:** at the end of `feed.jsonl` a 1 s poll. A rotation is detected by inode. Plain segments win over `.gz`, with a `.gz` fallback when the plain file vanishes between the listing and the open, and no segment is read twice.
  - **End:** `end` is sent once `ended_at` is set (checked at most every 30 s) and a final drain is done.
  - **Rotation:** a seek that finds the recording mid-rotation (the plain segment renamed to `.gz`, the next not yet created) waits for the new segment, as the tail does, instead of ending early.
  - **Limits:** a feed line is at most 8 MiB; beyond it the stream ends and logs the code `playback_too_large`. (The 16 MiB snapshot limit went with the snapshot load in P2e.) Recording files open with `O_NOFOLLOW`: a symlink is refused.
  - **Disconnect:** the client closing aborts the generator, whose `finally` closes the file handle and gunzip and clears the timers. Shutdown calls `server.closeAllConnections()` after `server.close()`, which would otherwise wait for open streams.
- **`CarData.z` and `Position.z` are not streamed** (owner, 2026-11-04): they are never applied, sent or kept in a stream's state. P3 can add them back behind a parameter.
- **Known and left** (owner, 2026-11-04): a reconnect's `Subscribe` state can roll back deltas that arrived just before it. It stays a follow-up, not part of P2d.
- **Delay slider (live only):** 0–120 s in 1 s steps plus ±1 / ±5 / ±30 s buttons, remembered per device in `localStorage` (`f1.delay`). Default 0 (the owner sets it). A replay ignores it, so its stored value never shifts a replay (owner, 2026-11-05).
- **Replay sync (P2):** the seek bar over [`started_at`, `ended_at`] with the session markers (A§13), plus ±1 / ±5 / ±30 s position nudges. The owner presses play on both the replay and the F1 TV replay, then nudges the position (the [owner] criterion: in sync after one adjustment within ±2 s for 10 min).

## 12. Security

### 12.1 Invariants

1. No secret in git, environment variables, image layers, logs or error messages. Secrets are files under `/etc/f1/secrets`, `root:<gid> 0440`, and only the consuming container has that GID.
2. Nothing is reachable without Cloudflare Access. The origin publishes only `127.0.0.1:8180` for the update smoke test, and `/api` checks the Access JWT itself.
3. Data from the F1 TV feed or the archive is never committed. Public fixtures for those parsers are synthetic, and real recordings stay in the gitignored `fixtures-private/` folder and on the VM.
4. CI never calls OpenF1, F1 or Jolpica.
5. The F1 stack shares nothing with Waterheight: networks, volumes, secrets, GIDs, ports, subnets, the nftables table, timers and the healthchecks group are all separate. Nothing touches `/etc/rws`, `/srv/rws` or the `rws` project.
6. Strict CSP as in Waterheight: `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; …`. The browser makes no third-party requests (no driver headshots from formula1.com).
7. Containers are hardened: `read_only`, `cap_drop: ALL`, `no-new-privileges`, non-root UID in its own range, memory/CPU/PID limits.

### 12.2 Cloudflare

- Its own tunnel, with its own `cloudflared` reaching only `caddy:80` (ADR-0004).
- An Access application on `<F1 hostname>`: an allow policy for the owner's email only, a session of 24 h–7 days, and email one-time PIN login.
- The `api` (`:8080`, inside the compose network only) checks the Access JWT itself (A§10). For that it makes outbound HTTPS to `<team>.cloudflareaccess.com` (Cloudflare's published ranges, A§14.3) for the team's certs, and reads the non-secret `CF_ACCESS_TEAM`/`CF_ACCESS_AUD` from `/etc/f1/f1.env`.

### 12.3 F1 TV credentials and token (ADR-0005)

- `f1tv_username` and `f1tv_password` are file secrets. The account has no 2FA, so automatic login works.
- The login is a TS port of FastF1's OAuth2 Authorization Code + PKCE flow against `id.formula1.com` (PingOne DaVinci, `response_mode=pi.flow`, all JSON calls). The access token's `subscriptionToken` claim is the Bearer token. It expires in ~4 days and has no refresh token.
- The token is cached in a file (0600, the live UID, written through a temporary name and a rename). On the host it is `/srv/f1/state/live/f1tv-token`; in the `live` container it is `/srv/f1/state/f1tv-token`, because only the subdirectory `/srv/f1/state/live` is mounted, as `/srv/f1/state` (owner, 2026-10-30). The state directory also holds `current.env`, which picks what root deploys, so a writable mount of all of it would let a compromised recorder choose that. The token itself is never logged; only its expiry is. The reader accepts only a regular file of at most 64 KiB with no group or other permission bits.
- **When it logs in** (owner, 2026-10-30): when a session starts within 48 h (or is running) and the token does not cover that session's end + 1 h. Not on a schedule, so a token that expired between weekends is no fault. The warning `token_expiring` shows when the token has under 24 h left, but only while a session is due within 48 h; `login_failed` shows on every failed login, whenever it happens.
- **Limits** (P2a security review, L2; P2c security review, M1): at most one login per 10 min, and one per 6 h after 3 failures in a row. A failure is a login that throws; one that returns a token that fails `checkToken`, equals the value the feed refused or still does not cover the session (`login_claims`; a token that is good for now is still saved and used); and one whose token the feed then answers with `feed_unauthorized` (which stays the last error). `login_failures` goes back to 0 only when a connection carrying a token that covers the session has subscribed, never when `login()` resolves, and that holds for a pasted token too. `login_failures` and `last_login_at` are in `recorder_status`, and the attempt is written before it starts, so a restart or a crash cannot turn into a sign-in storm. A failure sets the status and never exits the process. The login code sends the credentials only to `id.formula1.com`.
- A token the feed rejects (`feed_unauthorized`) is dropped, and the recorder goes on anonymously until the token file holds a different value.
- A token that cannot be saved (`token_file`) is no failed login: it stays in memory for this process, is used, and is written again every tick until that works or the file holds one that lasts as long. A token file that cannot be read for any reason but a missing file also shows `token_file`.
- **Egress is limited by port, not by host:** `live` can reach tcp/443 on any public IPv4 (A§14.3). The F1 hostnames are fixed only in the code (`redirect: 'error'`, the origin check on the login's `href`), so code running in `live`, a malicious dependency of the shared server image say, could send the password to any public host on 443. Accepted (owner, 2026-10-31): a filter by host behind CDN ranges costs more than it protects here.
- Fallback if the login breaks (bot protection, a flow change): the owner pastes the `login-session` cookie value from formula1.com, or a raw token, into the token file (as undercut-f1 does; `docs/runbooks/update.md`). The recorder reads the file every tick (30 s). The status panel warns as above, and a wrong owner or mode of the file shows as `token_file`.

- **`main`:** branch protection requires `ci` and `security`, enforced for admins, with no force-push or deletion, and a pull request before merging (0 approvals). Merge commits only.
- **Agent identity:** agents use the owner's admin OAuth token until P1f, when they move to their own fine-grained token without the Administration permission (A8). Until then "agents never merge" rests on the deny rules in `.claude/settings.json` and on the branch protection. The A8 token has contents, pull requests and issues read/write and no Workflows permission, so the owner pushes any diff under `.github/workflows` (owner, 2026-10-28). Agents switch to it before the first deploy from `main`.
- **Secrets:** `db_f1_migrator` is the first one. It lives in the `migrate` process and in the dbmate child's environment (readable through `/proc/<pid>/environ` by the same UID in the one-shot container). `DATABASE_URL` overrides it in dev and test; Compose never sets it, which the `hardening` check in `ci / deploy` enforces.

- **Accepted risks (owner, 2026-10-25):**

  - `npm`, `yarn` and `bunx`, `git push --prune` and `git -c … push` are not denied.
  - GitHub does not itself enforce SHA-pinned or allow-listed actions; `scripts/check-workflows.sh` and zizmor do, in files a PR can change.

### 12.5 Deploy path (P1f security review, 2026-10-29)

- **GHCR write access is code execution on the box:** `f1-update` runs whatever `:main` is, as containers with the db and its secrets. Hence the `production` environment on the `release` job (required reviewer: the owner; deployment branches: `main`), and the A8 agent token without Workflows. The `release` job holds `packages: write` behind that gate. Agents cannot merge: branch protection, the deny rules in `.claude/settings.json` (`gh api …/merge`, `gh api graphql`, `gh auth token`) and the environment approval.
- **`cf4`** lets the `api` reach any Cloudflare-fronted host on 443. Accepted: the api only fetches the team's certs.
- **`127.0.0.1:8180`** is reachable by local VM users: it serves the static site and `/healthz`; the api still checks the Access JWT.
- **New secrets:** `cf_tunnel_token` and `hc_ping_key`. **New egress:** hc-ping.com (`ingest`, tcp/443) and tcp+udp/7844 to the tunnel ranges (`cloudflared`).
  - **P2f amendment (2026-11-06):** `cloudflared` is pinned to `--protocol http2` and the udp/7844 egress is removed (A§14.3), so the tunnel needs tcp/7844 only. No new host, port, secret or GID.
  - **P2f: a new trust edge.** The root deploy timer reads `recorder_status`, which a container writes, through `docker exec f1-db-1 psql` (the first host script that execs into a container). Data a container writes now steers a host decision: `ingest` and `live` share the `f1_ingest` login (O3), so a compromised one can hold deploys, and a wrong `date_end` from OpenF1 does the same through the recorder's hard stop. The bounds are root-side: the query takes only a row under 5 minutes old and not more than 1 minute in the future, and `f1-update` deploys anyway after 14 h of unbroken deferrals (`held-since` in `/srv/f1/state`, `error: deploys held for over 14 h …`). So O3's shared login can delay a deploy by 14 h at most, not for ever.
  - **P2f: patch latency.** While `live` records, a deploy waits (before: 10 minutes at most): until the recording ends, at most 14 h. `sudo docker stop f1-live-1` ends the recording at once (`complete = f`) and lets the next run deploy.
- **P2c:** new secrets `f1tv_username` and `f1tv_password` (`root:62007 0440` and `root:62008 0440`, `live` only). New egress for `live`: the code talks to `account.formula1.com` and `id.formula1.com` (the login), `livetiming.formula1.com` (negotiate and the WebSocket) and hc-ping.com, all tcp/443 on `f1-egress`. The firewall does not hold it to those hosts: it allows tcp/443 to any public IPv4 (A§12.3, A§14.3), so there is no nftables change. The `live` container mounts `/srv/f1/live` and `/srv/f1/state/live` only; `hardening.sh` pins that bind list exactly (the `api`'s one bind is below).
  - **Core dumps are off** on every service (`ulimits: core 0` in the hardening anchor, `no_core_dumps` in `hardening.sh`, `docker inspect` in e2e): a dump of `live` would hold the F1 TV password and token, and a piped `core_pattern` would put it on the host.
  - **`ingest` shares the login that writes `recorder_status` and `recording`** (owner decision O3), so a compromised `ingest` could reset the login limits. A CHECK holds `recording.path` to `<digits>-<digits>`, because `live` joins it to a directory at boot.
  - **`/srv/f1/live` has no retention** (recordings stay replayable forever, ADR-0007) but a 1 GiB floor (A§11.2). The floor bounds the disk; a large buffer is contained by `mem_limit`.
- **P2d:** the `api` now reads the recordings, read-only (A§14.2). They are F1 TV data, private but not secrets, and the `api` is the only reader besides `live`. No new secret, egress host, port or privilege. The path comes from the `recording` row, never from the URL (A§10). The resource bounds: at most 8 streams per process, a speed of at most 16, and a memory per stream bounded by back-pressure (A§11.3). Error bodies are fixed, and the SSE route has no `onError`, because hono's `streamSSE` would write the error's message to the client.
  - **A new file trust boundary:** the `api` parses files that `live` wrote (the feed lines; since P2e not the snapshots). A compromised `live` could write hostile files, so the parsing is bounded by the limit of A§11.3 (a line 8 MiB) and the files open with `O_NOFOLLOW`.
  - **Accepted Low, stream lifetime:** the Access JWT is checked at connect only, and a stream is neither capped in lifetime nor ended at the JWT's `exp`. Accepted: the owner is the only Access user. A stalled client is bounded by the 60 s write timeout (A§10).
- **P2e:** no new secret, egress host, port or privilege, and the CSP is unchanged (the web has no new third-party request; the stream is a same-origin `EventSource` to `/api`, behind Access). The `api` now replays a recording from its first line on every stream open (A§11.3): a full scan per open, bounded by the 8-stream cap, the 8 MiB line limit and the 60 s write timeout. `/api/v1/recordings` returns the `recording` table joined to session and meeting, behind the same Access check. The browser renders feed text (driver names, race-control messages, the track status) as text only, never as HTML.
- **Root:** three systemd units drive Docker as root: `f1-firewall`, `f1-update` and `f1-tick`. Their scripts are root-owned copies in `/usr/local/bin`; the timers never run a file of the checkout.

(owner, 2026-11-07, P4e): `/replay/:recording` takes an optional `?t=HH:mm:ss`. `routeOf` keeps the path rules and ignores the query; the query belongs to the player (URL state, below).
  - A meeting or session segment is `<key>-<name>`, such as `/2026/1290-singapore/9965-race/laps`, and parses as `^(\d{1,9})(?:-[a-z0-9-]*)?$`. The key decides; the name is decoration (lower case, diacritics stripped, other runs → `-`; meetings drop a trailing ` Grand Prix`). Once the session is loaded, a wrong or missing name, year or meeting key is replaced by the canonical URL (`history.replaceState`). `/:year/:meeting/:session` goes to `…/laps`.
  - **`?d=`** (owner, 2026-11-07, P4f): the one query the routes know. It belongs to the session view's `compare` and `minisectors` and holds the picked drivers (Driver picker below). `routeOf` still reads the pathname only; the canonical-URL `replace()` keeps `location.search`, and `navigate()` moves focus to the h1 only when the path without its query changes.
  - **`/`** (owner, 2026-11-07, P4c, D1): goes to `/live` while `/live` (A§10) names a recording with `ended_at` null; else to `/:year` of the newest season whose `/seasons` row counts a non-cancelled session; else "No seasons yet.". It never lands on a lap table, so a result is not the first thing on screen. It waits for `/seasons` and `/live` (an error in `/live` counts as nothing open) and redirects with `replace()`. This replaces the old walk to the last started session's lap table. It never jumps to next year during a season: the schedule sync (A§8) lists a year only from 1 January, as it syncs up to the current UTC year. The trade-off: while a recording is open (until `SessionStatus: Ends` + 30 min, A§11.2), `/` opens `/live`, whose tower is in running order; that is the owner's rule (D1), and it is not a lap table.

  - **Lap table** (owner, 2026-10-28): a drivers × laps matrix with one time per cell. A segmented control `Lap | S1 | S2 | S3` picks the metric, and a toggle puts the drivers in rows (default: a sticky driver column with a 4 px team-colour bar, lap numbers as the header row) or in columns (a sticky lap column, drivers as the sticky header row). Both are component state, not URL state.
    - The colour is the cell's text colour, for the bests only: "other" values (the server's yellow) are plain text (owner, 2026-11-07, O1). Since P4b (owner, 2026-11-07) the cues are: other plain, purple boxed (a 2 px outline on a `--purple-wash` tint) and bold, green bold, in- and out-laps in `--dim`, a deleted lap struck through. Colour is never the only cue: a screen reader hears ", overall best" or ", personal best" after a ranked purple or green value, and a legend under the metric switch shows the styles ("overall best", "personal best", plain "other", in-lap with its IN badge, a new stint, deleted, and the SC/VSC or red-flag lap when the session has one; in the Δ view the four heat steps instead). On a ranked lap the cell's `title` names its colour (overall best, personal best, slower than personal best); a deleted lap, an in-lap or an out-lap has no such title, because the server colours all its values yellow without ranking them (A§9). The table has an accessible name per metric ("Lap times", "S1 times", …).
    - A deleted lap is struck through in every metric; a missing value shows `—`. The reason sits behind the cell in a tap popover opened at its cell (Popovers; `ui/Note.tsx`: a `<button popovertarget aria-describedby>` plus a native `popover`, so a tap works on a phone with no JS state; the `title` serves a hover). It is the deletion reason, or why the value is missing: an out-lap (S1, and the lap time on lap 1), an in-lap, race lap 1 from the grid, else "No time in the OpenF1 data". These are the cases the P1d null probe over every session since 2025 shows to be real.
    - PIT IN/OUT badges (owner, 2026-11-07, P4b): IN on an in-lap, OUT on an out-lap only where no compound dot starts the run (the dot already says the set is new). The compound dot (S/M/H/I/W) marks the first lap of each run per driver (a new compound, or new tyres out of the pits), not every cell. It is `aria-hidden`, with "soft tyres, " beside it for a screen reader (the laps carry no tyre age, so no "used set" here). A run start after the driver's first lap also gets a 2 px `--line` rule on the cell's leading edge (left in rows mode, top in columns mode).
    - **Frozen columns** (owner, 2026-11-07, P4b): in rows mode the Driver column (72 px) and a Best column stay in view, Best sticky at `left: 72px` with `min-width: 112px` (80 px under 600 px, where its lap number is hidden and kept in the `title`). Best is the driver's own best valid value of the metric (not deleted, in or out, A§9) in the server's colour (purple, green or plain), with its lap number small beside it ("L12"); without one it is `—` with a reason behind a tap ("No valid lap time", "No valid S2 time"). Columns mode puts Best in a second `thead` row under the driver names; the whole `thead` sticks. `scroll-padding` keeps a focused cell clear of them: rows mode 190 px on the left (158 px under 600 px), columns mode 88 px on top.
    - **Track bands** (owner, 2026-11-07, P4b): the lap number in the header gets a 3 px band and its label (`SC`, `VSC`, `RED`) for each lap inside a period of `trackPeriods` (A§6.1): `--amber` for the safety car and VSC, `--live` for a red flag, on the left of the lap number in columns mode. Where periods overlap on a lap the most severe wins the band and the label (red, then safety car, then VSC), and the `title` lists every kind most severe first ("Safety car, virtual safety car"). The bands come from `race_control`, fetched for races and sprints only and not at all when the session has no laps; the table shows at once and gains its bands when they arrive, and a failed fetch says "Race control did not load: no SC, VSC or red-flag bands.". Rows in a period form without a lap number are listed under the table ("No lap number in the data, not banded:", time and message as text), never banded. A band marks the leader's lap (A§6.1), so a lapped car's cell can be a lap off.
    - **Times | Δ to own best** (owner, 2026-11-07, P4b; D3): a second segmented control, component state like the others. Δ replaces each value with its gap to the driver's own best for the metric, `+0.41` (two digits; three under 10 ms, `+0.003`, so a slower lap never reads `+0.00`), or "best" on that lap (boxed in its colour); a lap without a value keeps `—` and its reason, and a lap that is no valid time shows a word instead: "deleted", "in", "out", or "SC", "VSC" or "RED" on a banded lap. The cell's background takes one of four heat steps from the gap as a share of the own best (`--heat-1..3`): none below 0.5 %, step 1 below 1 %, step 2 below 2 %, step 3 at 2 % or more, the same for the lap and S1–S3. The text carries the value, so the step is never the only cue. The table is named "<metric> Δ to own best", and the legend shows the four steps ("< 0.5 %", "< 1 %", "< 2 %", "≥ 2 % slower than own best").
    - Drivers by result position (nulls last), then number; drivers without laps are left out. A session without laps says "No laps yet".
  - **Session tiles** (owner, 2026-11-07, P4b; `views/Tiles.tsx`, `lib/bests.ts`): above the lap table on the Laps tab, six tiles in a grid (`dl.tiles`, "Session bests"): Fastest lap, Best S1, Best S2, Best S3, Sum of best sectors and Top speed. The sum is the best S1 + S2 + S3 and is called "sum of best sectors", never "ideal lap", with its Δ to the fastest lap behind it ("+0.31 to the fastest lap"). Top speed is the largest speed trap `st_kph` on a valid lap, with its holder and "speed trap". A tile without a value shows `—` and a fixed reason behind a tap: "No valid lap with a time", "No valid S1 time" (S2, S3), "Needs a valid time in S1, S2 and S3", "No speed-trap reading on a valid lap".
  - **Qualifying by phase** (owner, 2026-11-07, P4b; D1 to D4; `views/QualiTable.tsx`, `lib/quali.ts`): for Qualifying-type sessions (sprint qualifying and the 2023 Sprint Shootout included, their phases named SQ1–SQ3) the Laps tab opens on a `By phase | Every lap` switch (component state, By phase first), Every lap being the lap table. Without any `quali_phase` it says "No qualifying phases in the data: see Every lap.". One row per driver of the results (and of the laps), one column per phase, then To pole and Timed laps.
    - **Cells:** the driver's best valid lap in that phase (by `quali_phase`, A§9), with a margin to the phase's cut-off in small text under it: `−0.212 inside`, `+0.105 out` or "on the cut-off". The phase's fastest time is boxed purple. A `DEL` badge behind a tap lists the driver's deleted laps of that phase (time, lap and reason). Without a time the cell is `—` with a reason: "Knocked out in Q2" for a later phase, "No valid lap in Q2", or "No laps in the data" for a driver with no laps, who sorts last.
    - **Through rule** (D1): a driver went through phase p if they have any lap row with `quali_phase` p + 1, timed or not, so a Q3 crash on the out-lap counts. The limit: a driver who goes through but never leaves the garage shows as knocked out (a `ponytail:` note in `quali.ts`; the upgrade is the official classification).
    - **Cut-off:** the slowest best among the drivers who went through, with the count of them as the position ("Q1 cut-off (P16)"); nothing is hard-coded to 15, 16 or 10, so a field of 20 or 22 works. The last phase has none.
    - **Knock-outs** (D4): a 2 px `--fg` line under the last driver through each phase, with a label row (it keeps the 44 px row height) in the 12 px label style, "Q3 above · knocked out in Q2 below" (`--live` would break the token rule above). The rows are ordered by the highest phase reached, then by the best in it, then by result position, then by number. To pole is the driver's best in the last phase minus the pole time ("pole" for the pole sitter, else `—` with "Not in Q3"); before a third phase has laps the column is To fastest, against the last phase's fastest ("fastest", "Not in Q2"), because the three-phase format is assumed; Timed laps counts laps with a time that are neither in nor out, deleted ones included.
    - **Tiles** (D2): above the six session tiles, a "Qualifying" row with Pole (time, driver and phase; "Fastest in Q2", or SQ2, until a third phase has laps) and each phase's cut-off but the last ("Q1 cut-off (P16)", the holder's acronym; `—` "Known once Q2 has laps" before the next phase has laps).

    - **Chart:** ECharts in a lazy chunk. `lib/echarts.ts` is the only runtime import of it, `views/Chart.tsx` its only importer, and the chart views `views/Compare.tsx` and, since P5a, `views/Weather.tsx` its only users (`build.test.ts` checks both; owner, 2026-11-07). `Chart({ label, option })` loads it with `import()` and shows "Loading…" meanwhile, or "Chart failed to load: reload the page."; the canvas renderer, full width with its height from CSS (`.chart`); the lap chart and the gap chart share the one chunk. Every series has `symbol: 'none'` and `showAllSymbol: true`; the laps below override the symbol. The line has the team colour (else `--muted`; on the light theme `clampForLight`) and a line type (C2, below).
      - **Window** (a "Window" switch Fit | 107 %, component state, Fit by default): both start at `min = floor(best − 1 s)` to a whole second, where `best` is the fastest valid (purple or green) lap of the picked drivers. Fit (owner, 2026-11-07, P4f, C1) ends at `max = min + 4 s`; 107 % keeps its old end, 107 % of `best` ceiled to a second. The y axis ticks every second, labelled "1:33". A lap above `max` runs off the top and stays in the tooltip; without a valid lap the axis scales by itself.
      - **Symbols:** the own best (the lap coloured purple or green, as `DeltaTable`'s `bestOf`) is a 10 px circle in the team colour with a 2 px `--bg` ring (the stroke sits on the edge, so it reads as an 8 px dot inside a ring). A deleted lap is a 10 px circle filled with `--bg` and ringed 2 px in the line colour.       - **ECharts 6.1 facts behind that** (checked in its source and by the 390 px render test): an `emptyCircle` is filled `#fff` (`tokens.color.neutral00`), a white disc on the dark theme, hence the circle filled with `--bg`; a `markArea` on a category axis runs from category centre to centre, so a one-lap period would have no width, hence the value axis (0.5 … last + 0.5, labels on whole laps only) and a band from `from − 0.5` to `to + 0.5`; `showAllSymbol: 'auto'` thins symbols only on a category axis, so no symbol is thinned on the value axis and `true` stays as a backstop; the line `symbolSize` default is 6 (the symbols here are 10 px and 8 px); `endLabel` plus the `LabelLayout` feature's `moveOverlap: 'shiftY'` keeps the end labels apart; and a markArea on a driver's series goes when the legend hides that driver, so the bands sit on their own series.

The gap chart needs no such rule: its y axis scales to its data. The grid uses `outerBoundsMode: 'same'` and `outerBoundsContain: 'axisLabel'`, ECharts 6's replacement for the deprecated `containLabel`.

      - **Line types** (C2, owner, 2026-11-07, P4f; `lineStyles`, shared with the gap chart): each driver's colour as drawn in the current theme (the team colour on dark, `clampForLight(team)` on light, `--muted` without a team colour). A driver's crossing after lap n is lap n+1's `date_start`, else lap n's `date_start + lap_ms`, else null; the gap is its crossing minus the reference's at the same lap count, so a lapped driver shows a gap of over one lap and its line ends at its own last lap. On `error` the client closes the EventSource itself and the player reopens after a backoff of 1 s, doubling to 30 s (reset by the next `snapshot`), at the current T (clamped into the recording), or at `live` when it was live. An event that fails its contract is treated as an error. After `end` it never reopens.

It is checked every second against the wall clock, so a resumed page with a dead stream reopens within a second, and a healthy stream, whose events kept arriving, is not reopened. There is no `visibilitychange` handler.

### 14.3 Firewall

- A separate `table inet f1`, loaded by `f1-firewall.service` (oneshot, `nft -c` then `nft -f`, never `flush ruleset`).
- Forward hook on `f1-*` interfaces only:
  - DNS to the host resolvers
  - tcp/443 from `f1-egress`, to any public IPv4: the limit is the port, not the host. `ingest` and `live` share this network, and their hostnames (OpenF1, F1, hc-ping.com) are fixed only in the code (A§12.3)
  - tcp/7844 from `f1-tunnel` to Cloudflare's tunnel ranges (P2f: `cloudflared` runs `--protocol http2`; on the VM QUIC (udp/7844) fails with `tls: no application protocol` and cloudflared fell back to http2 only after ~130 s, longer than the 120 s smoke test, seen 2026-11-04)
  - tcp/443 from the `api` (`f1-api-egress`, shared with no other service) to Cloudflare's published IP ranges only, for the Access certs (owner, 2026-10-26, P1c). Port 8080 is never published, and Caddy↔api stays on the internal `f1-edge`
  - drop everything else (all of `f1-publish`'s egress included), plus host-input drops for `f1-*` (only established/related replies pass: docker-proxy's path for 8180)
- DNS is allowed only from the three egress networks (`f1-egress`, `f1-api-egress`, `f1-tunnel`), to the set `resolvers4`, and before the drop of private ranges (the resolvers may be on the LAN). The private ranges are dropped even on 443. Traffic from an `f1-*` bridge to another `f1-*` bridge is `return`ed to Docker's own internal and icc rules.
- Sets (fetched 2026-10-29): `cf4` from `https://www.cloudflare.com/ips-v4`; `cf_tunnel4` = 198.41.192.0/24 and 198.41.200.0/24 from Cloudflare's "Tunnel with firewall" documentation; `resolvers4` is filled by `f1-resolvers` from the host's resolv.conf (an `ExecStartPost` of `f1-firewall.service` and every `f1-tick`). The owner refreshes `cf4` and `cf_tunnel4` by hand (`docs/runbooks/cloudflare.md`).
- Without this table a second project's egress is unrestricted, because Waterheight's table only matches `rws-*` and `docker0`.

### 14.4 Updates

- CI on `main` (the `release` job, in the GitHub environment `production`: it waits for the owner's approval before it touches GHCR, owner 2026-10-29) builds both images, pushes `ghcr.io/mwijkhuisen/f1-server` and `f1-web` as `:main` and `:sha-<git>` (public, no secrets inside), and records the digests. The job's `concurrency` group queues runs without cancelling, so `:main` stays on the newest commit.
- `f1-update.timer` (every 10 min) runs `deploy/bin/f1-update`:
  1. take a flock; refuse (exit 1) when `table inet f1` is not loaded
  2. `docker pull` `:main`; wait (exit 0) while the two images' `org.opencontainers.image.revision` labels differ (a release half pushed); stop if the digest equals `current.env`; stop with a loud log line if the pair equals `failed.env` (a known-bad pair is never retried automatically; `rm /srv/f1/state/failed.env` to retry)
  - **Hold (P2f):** defer while `live` records. `f1-update` asks `recorder_status` (through `docker exec f1-db-1 psql`, 20 s at most) for a row whose `state` is not `idle` and whose `updated_at` is under 5 minutes old. If there is one, it removes `candidate.env`, logs `live is recording (session N): deploy deferred to a later run` and exits 0, and the next run retries. A deploy recreates `live` and ends its recording with `complete = false` (A§11.2). It fails open: no db container, an unreachable db or a stale row (`live` is down) does not hold, and the query logs `warning: cannot read recorder_status: deploying without the hold` when it fails. The row must also be no more than 1 minute in the future, and root caps the hold: `/srv/f1/state/held-since` holds the epoch of the first deferral of an unbroken chain (its mtime is the last deferral; a gap over 30 minutes starts a new chain), and after 14 h `f1-update` logs `error: deploys held for over 14 h (session N, since <UTC time>): deploying anyway; check recorder_status` and deploys (A§12.5). It removes `held-since` when a deploy starts. A drill (`--server`/`--web`) is held too. To deploy a fix during a recording at once: `sudo docker stop f1-live-1`, then `f1-update`. `f1-install` has no hold.
  3. run `migrate`
  4. `up -d`
  5. smoke-test `http://127.0.0.1:8180/healthz`, then require every f1 container healthy (an unhealthy `ingest`, `live` or `cloudflared` fails the deploy)
  6. on failure, write the pair to `failed.env` and roll back to the previous digests in `/srv/f1/state/current.env`
- State lives in `/srv/f1/state`: `current.env` (the last pair that passed), `candidate.env` (during a run), `failed.env`.
- `f1-update --server <ref> --web <ref>` deploys the given images instead (drills, CI); the flag not given keeps the image of `current.env`, and the revision check is skipped. A ref with a registry host is always pulled and recorded by digest, so `current.env` never names a movable tag; only a host-less local ref (`f1-server:ci`) is recorded as given.
- GitHub has no server credentials.
- `f1-update` deploys nothing (`not configured`, exit 0) while `f1.env` or any file in `F1_SECRETS` is empty, so after P2c adds `f1tv_username` and `f1tv_password` deploys pause until the owner fills them. The rollout order is in `docs/runbooks/update.md`: the image first, then `f1-install`, because an image from before P2c exits 2 on `live`.
- Compose, Caddyfile, nftables and units change rarely. The owner applies them with `deploy/bin/f1-install` from a checkout on the VM. It is idempotent, re-applies a changed compose file to a running deploy, and does not enable the timers: the owner does that once the secrets and `f1.env` are filled (`docs/runbooks/install.md`).

### 14.5 Operations

- **`f1-tick.timer`** (every 10 min, at :05): reloads `table inet f1` if it is missing, refreshes `resolvers4`, restarts unhealthy `f1` containers (Docker doesn't) and records disk usage in `/srv/f1/state/disk`. Fail closed: when the table cannot be loaded, it stops every `f1` container and writes `/srv/f1/state/firewall-stopped`; once the table loads again, `f1-tick` or `f1-update` starts `current.env` again. Restarts and the restart of a stopped stack run under `f1-update`'s lock and are skipped for that round while a deploy or `f1-install` holds it.
- **`f1-measure`** (P2f, [box], root only; `f1-install` installs it into `/usr/local/bin`): `f1-measure <duration> [<interval s>]` (the interval is the pause between samples; a sample takes 2-3 s) samples CPU, memory and disk of the f1 containers only (the compose project `f1`, never Waterheight's) into `/srv/f1/state/measure-<UTC>.tsv` (`0600`) and prints a Markdown summary (per service: samples, CPU mean and max %, memory max against its limit, OOM kills, exits, restarts, counted from `docker events` (`State.OOMKilled` is reset by a restart); disk growth of the recordings, the db volume and each container's logs). `--summary <file>` rebuilds it from a TSV. It tunes the limits of A§14.2; the runbook is `docs/runbooks/weekend.md`.
- **healthchecks.io:** uses the 2 free checks left on the account: `f1-ingest` (pinged once the sync requested by the daily `30 0 * * *` Cron, or its 15-minute retry, has succeeded; not after the startup sync, so a crash loop does not stay green; period 1 day, grace 1 h) and `f1-live` (P2c): `live` pings it once when a recording ends complete (A§11.2), and pings `f1-live/fail`, which alerts at once, when one ends incomplete at a normal stop or ends on a disk failure or the floor. A recording that a restart cut short therefore ends in a fail. Neither ping comes for a cancelled or moved session or for a SIGTERM (a deploy). Beyond that silence is the alarm, so the check's period suits the gaps between race weekends (owner's choice).
- **Logs:** pino JSON to Docker's `local` driver (host daemon defaults). Fixed codes only, never URLs with tokens.

## 16. Risks

| Risk | Mitigation |
|---|---|
| F1 changes access again (as in Oct 2026) | OpenF1 is the v1 source. Raw responses and recordings are kept. Spikes run before each build phase |
| OpenF1 gaps, slowness, re-ingests | Refetch at +3 h/+24 h, `refetch` command, honest gaps in the UI |
| F1 TV login flow changes / bot protection | Manual token-paste fallback. Expiry warnings |
| Token expires mid-session | Pre-check before connecting. Logs in again on 401 and reconnects |
| GitHub/cloud IPs blocked by F1 | All F1 traffic from the home VM. CI uses fixtures only |
| F1 TV ToS (personal use) | Single-identity Access, no public data, no commits of F1 TV-derived data |
| Resource contention with Waterheight | Strict container limits, VM resize, measurement after backfill and the first live weekend |
| Only 6 race weekends left in 2026 | Record all of them early (P2-rec), then build P2 over the winter on those recordings |
| Lap reconstruction from the feed is hard | Port FastF1's logic deliberately and compare against OpenF1 laps for the same session as a test oracle |
